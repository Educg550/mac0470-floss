Atividade 01/07/2026

Escolha do projeto (etapa 2)​

Chegou a etapa 2 e minha dupla (Lucca Ciriac) optou por contribuir para o cregit, que é o tema do TCC dele. Eu, porém, depois da palestra da penúltima aula, fiquei com vontade de seguir por outro caminho: contribuir para o KDE. Já uso há bastante tempo várias ferramentas do ecossistema: KDE Neon, Okular, Kdenlive, KWrite, entre outras. Então retribuir para algo que eu mesmo aproveito tanto fazia todo sentido.

Com base no que foi apresentado na palestra, fui atrás do guia de contribuidores do KDE e achei tudo muito bem documentado. Uso Linux Mint LMDE, mas mesmo assim montar o ambiente de desenvolvimento do Kdenlive foi bem simples via distrobox e podman.

O bug escolhido​

Fui procurar junior jobs no Bugzilla e dei de cara logo com o Kdenlive, um software que eu já conhecia e usava bastante. Acabei pegando um bug que, surpreendentemente, já tinha me irritado como usuário: bug 498136 | "Add as a new Title" should replace existing Title clip in Timeline.

O problema era: ao editar um clipe de título a partir da timeline e escolher "Add as a new Title", o novo título ia apenas para o Project Bin, mas o clipe antigo continuava na linha do tempo, ou seja, a substituição precisava ser feita na mão. O esperado é que o novo título fosse adicionado ao Project Bin e substituísse o clipe de título que estava sendo editado na timeline.

A contribuição​

Consegui resolver o problema no final de junho e abri o merge request !907 já no dia 01/07. A ideia central foi fazer o showTitleWidget() "saber" de onde a edição partiu: se veio de um clipe da timeline, o Kdenlive passa a perguntar se o usuário quer substituir aquele clipe (com opção de "não perguntar novamente") e, em caso positivo, usa processTimelineReplacement() para trocar o clipe preservando posição, pontos de in/out e efeitos.

A janelinha de confirmação introduzida pela correção:

Resumo do diff (simplificado):

// src/bin/bin.h | showTitleWidget agora sabe de onde veio a edição
-void showTitleWidget(const std::shared_ptr<ProjectClip> &clip);
+void showTitleWidget(const std::shared_ptr<ProjectClip> &clip,
+                     int timelineClipId = -1,
+                     const QUuid &sequenceUuid = QUuid());

// src/timeline2/view/timelinecontroller.cpp | editTitleClip()
-pCore->bin()->showTitleWidget(clip);
+pCore->bin()->showTitleWidget(clip, clipId, sequenceUuid);

// src/bin/bin.cpp | showTitleWidget(): ao "Add as a new Title"
+// se a edição partiu de um clipe da timeline, oferecer a substituição
+if (timelineClipId != -1 && /* usuário confirmou (com "não perguntar de novo") */) {
+    // troca o clipe preservando posição, in/out e efeitos
+    timeline->processTimelineReplacement(timelineClipId, newId, sequenceUuid);
+}

Arquitetura do Kdenlive​

O que mais me ajudou a entender o código foi a pasta dev-docs, em especial o documento de arquitetura. Em resumo, o Kdenlive é basicamente uma interface (GUI em Qt/QML) construída em cima do MLT: é o MLT core que faz o trabalho pesado de renderização, playback, efeitos e composição de vídeo. O código do Kdenlive se organiza em torno de models (por exemplo o modelo da timeline) que traduzem as ações do usuário para o MLT, enquanto a parte visual apenas reflete esse estado.

Comparação com o kernel​

No geral, foi muito mais fácil que contribuir para o Linux kernel (etapa 1). Dois motivos:

  • Eu já tinha bastante familiaridade com abrir PRs/MRs no GitLab, então o fluxo do invent.kde.org foi natural. Bem diferente do fluxo de patches por e-mail (git send-email + lore) do kernel.
  • O guia de contribuição do KDE e do Kdenlive é muito completo e beginner-friendly, e a pasta dev-docs me poupou um tempo enorme para entender a arquitetura antes de mexer no código.

Atualização (07/07)​

Demorou um bocado até revisarem, mas ontem (07/07) o MR foi mergeado e já está na branch master do Kdenlive. O revisor Jean-Baptiste Mardelle aprovou mesmo apontando um detalhe fora de escopo:

Thanks a lot for your contribution. There is a small issue where clips longer than the default title duration will not be replaced, but it also depends on a small issue in TimelineItemModel::processTimelineReplacement, so will fix it after the merge.
